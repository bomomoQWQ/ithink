# 插件公开 API 与生命周期

状态：协议版本 1，实验性接口，尚不承诺稳定 ABI。本文以当前代码为准，不是完整操作系统或安全沙箱设计。

## 1. 内核控制启动

插件是独立的可执行程序。宿主向 `Runtime` 提供 `PluginSpec`，包含程序路径、参数、工作目录、附加环境、能力集合、工作层级、依赖和提供的服务。

- `begin_load(spec)`：立即启动并返回加载票据；宿主继续调用 `pump()`，通过 `take_load_result()` 收取结果。
- `load_plugin(spec)`：方便的等待版本；等待期间仍推动其他插件请求，但该宿主调用本身要等加载结束。
- 已存在同名插件时，加载变成热替换。
- `unload_plugin(name)`：撤销主体、订阅和服务路由，使待办调用失败，终止插件进程树。仍有显式依赖时拒绝卸载。

热加载指**不重启整个内核的进程加载/替换**，不是把动态库注入内核地址空间，也不是自动监听文件。

宿主可选提供 `PluginSpec.bootstrap = Some(BootstrapInput::json(...))`，在公开握手前通过子进程 stdin 写一行最多 64 KiB 的私有 JSON。支持此启动方式的插件先消费该行，再调用普通 SDK；未使用该选项时协议不变。它适合交付凭据等启动配置，不经过内核请求/上下文/日志，Debug 隐藏内容。它是可信宿主与可信插件之间的管道，不是恶意插件隔离或系统凭据保险箱。

## 2. 握手

标准输出只放协议，诊断写标准错误。每一行是一个 JSON 对象，含换行的最大帧为 1 MiB。

```text
插件 -> 内核：ready（版本、插件名）
内核 -> 插件：welcome（AID、实例代数）
插件 -> 内核：activated（接受身份并完成本地初始化）
内核：校验存活、依赖、服务路由，切换当前实例
内核 -> 插件：active
随后：request / response / notice
```

新实例握手失败、超时或初始化期间退出，不撤销旧实例。握手完成后仍可能崩溃，内核不承诺永久健康。旧进程退出后，迟到消息因实例代数不符被忽略。

实例获得新 AID；旧上下文和进程内状态**不自动迁移**。应用若需要连续性，应先把状态明确保存，再由新实例读取或由父主体重新赋予任务。

## 3. 公开请求

精确结构见 [api.rs](<../src/api.rs>) 和 [protocol.rs](<../src/protocol.rs>)。

| 类别 | 操作 |
|---|---|
| 主体 | `AgentCreate`、`AgentGet` |
| 任务 | `TaskCreate`、`TaskGet`、`TaskFinish`、`TaskCancel`、`TaskFail` |
| 上下文 | `ContextAppend`、`ContextGet`、`ContextRead`、`ContextReplace` |
| 事件 | `EventSubscribe`、`EventUnsubscribe`、`EventPublish` |
| 插件 | `PluginStart`、`PluginStop` |
| 系统桥 | `SystemCall`、`TaskSystemCall`、`BackendRegister`、`BackendComplete` |

所有请求只携带请求编号，不携带可自由填写的“当前调用者”。内核根据进程连接绑定 AID。编号在同一连接中严格递增，重复或倒退是协议错误；不能把重试当幂等支持。

`AgentCreate` 仅创建主体记录。需要真正运行的子代理应使用 `PluginStart`。

### 父主体与工作代理

宿主先注册程序模板 `register_template()`，明确允许执行哪个程序和拥有哪些能力。上层主体只有同时持有 `kernel.plugin` 和 `launch:模板名` 才能请求启动该模板，不能任意传入系统命令。参数中完全等于 `{name}` 的项会换成实例名。

- 一般 `AgentCreate` 的能力不得超过父主体。
- `PluginStart` 使用**宿主预授权模板**，可委托父主体本身没有的工具能力。这让主代理能派活而不必自己持有执行工具；它不能自行改模板或增加能力。
- 子主体层级必须低于父主体（数字更大）。层级不赋予 CPU 优先级或文件访问权。
- 父/祖先可创建、赋予初始上下文、查询生命周期、取消后代任务。
- 任务后续上下文读写只允许任务所属主体或宿主；管理权限不自动授予读取后代私有上下文的能力。
- 完成结果和结束通知交给任务所属主体及上级。通信没有固定 Router/Worker 拓扑。

## 4. 系统桥

宿主配置 `服务 + 操作 -> 所需能力`；后端提供者不能降低要求。

```text
宿主 define_operation("files", "read", "files.read")
宿主 define_operation("files", "write", "files.write")
后端插件声明提供 files，持有 kernel.backend 和 provide:files
调用者请求 files/read
内核校验调用者能力 -> 发给后端 -> 原样封装返回
```

`define_service()` 是显式的通配便利接口：配置的是该服务的**所有操作**。如果需要读写分权，应使用 `define_operation()`，未声明操作默认拒绝。

后端收到的通知含内核绑定的调用者 AID、可选任务编号、调用编号、操作和参数。路径范围等细粒度策略可由后端执行，但不能信任参数中自报的调用者身份。

返回区分两类：

- 内核错误：未授权、超时、插件退出、协议错误等。
- 后端结果：`BackendResult::Ok(原生内容)` 或 `BackendResult::Error(原生错误)`。内核不修改其中字段和错误消息。

慢调用只登记待办并发送事件，不阻塞内核等待结果。超时或任务取消会结束待办、通知后端取消；后端应实现协作取消。已经产生的副作用不保证撤回，超时不等于“没有执行”。

## 5. 上下文与压缩

- 初始内容由创建任务的一方明确提供，不隐式继承整份父上下文。
- 一个任务的窗口单独核算，不将父子多个模型窗口相加。
- `units` 是调用方/计量器提供的单位，内核不伪称精确 token 数；`opens` / `closes` 是插件声明的配对 ID。
- 到压力线发通知，硬上限拒绝写入；不静默删旧消息。
- 插件生成摘要，再提交 `ContextReplace`；替换带预期版本号和半开范围 `[start,end)`。成功会向所属主体发送 `ContextReplaced` 通知，便于暂停的用户态循环恢复。
- `ContextRead` 还返回 used、threshold、max_input 和 pressure，调用方不需要另存一套压力判断真相。
- 版本不符、切断配对、修改固定项、没有缩小、超过硬上限时，整个替换失败，不部分改写。
- 原始内容保留在该上下文的只增日志中；当前视图变化可确定回放。历史日志目前在内存，整核磁盘恢复尚未实现。
- 大上下文通过 `ContextRead(start,limit)` 分页；写入操作只返回用量/版本，完整读取过大时回 API 错误，不当作插件崩溃。

内核不硬编码某个模型的前缀缓存规则。未替换的内容保留原样。压缩仍会改变后续模型输入和缓存，这个取舍属于用户态策略。

## 6. 故障与资源边界

进程收发都有有界队列，JSON 解析前限制帧长。过载会显式断开故障插件，不无限缓存。上下文内容与事实日志没有实现磁盘轮换，长期运行仍需补充存储与保留策略；不能把有界传输误说成总内存有界。

Windows 使用 Job Object 清理进程树，阻塞管道调用可被取消；Unix 使用独立进程组。进程退出和线程回收由共享清理线程处理，不在内核循环无限等待。Windows 创建与加入 Job 之间仍有短暂间隔，Unix 主动脱离进程组也不保证拦截——这些机制**不是防恶意插件的沙箱**。

当前没有插件安装/下载/升级市场、自动文件监控、热状态迁移或持久性主代理监督器。真实模型请求由可选的用户态 [OpenAI 兼容适配器](<../src/openai.rs>) 和 [独立进程插件](<../src/bin/model_provider.rs>) 提供，不是内核内建策略。
