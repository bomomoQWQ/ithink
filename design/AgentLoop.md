# Agent Loop：首版实现

2026-11-15。可替换的用户态循环组件，不是内核必须采用的唯一 Agent 形态。

## 1. 循环做什么

```text
读取任务上下文
  -> 请求模型
  -> 校验模型输出
  -> 把模型输出写入上下文
  -> 有工具调用？
       是：按已注册路由执行工具 -> 写回结果 -> 再请求模型
       否：提交任务完成
```

一个任务对应一个循环。一个插件进程可推动多个循环：某个任务等待模型/工具时，不需要等它返回才能处理另一个任务。

**不内置**会话、人格、记忆、主子代理拓扑、在线模型协议或默认摘要策略。

## 2. 分层

| 文件 | 职责 |
|---|---|
| [agent_loop.rs](<../ithink-core/src/userland/agent_loop.rs>) | 纯状态机：给出下一条公开 API 请求，接收结果，推进状态；自身不执行 I/O |
| [loop_plugin.rs](<../ithink-core/src/userland/loop_plugin.rs>) | 用户态进程驱动：把多个循环的局部请求编号映射到 SDK 连接编号 |
| [sdk.rs](<../ithink-core/src/kernel/sdk.rs>) | 完成握手、发送请求、后台读取帧；新增有界 `poll/take_response/take_notice` |
| [loop_fixture.rs](<../plugins/loop-fixture/src/main.rs>) | 假模型、加法工具与循环插件示例，全部走公开 API |
| [loop_demo.rs](<../demos/loop-demo/src/main.rs>) | 启动上述进程、创建任务并打印结果 |

内核增加的只是通用机制：

- `TaskFail`：由任务所属主体明确提交失败状态。
- `ContextRead` 补充压力与容量信息。
- `ContextReplaced`：通知所属主体上下文已被替换，等待压缩的循环可重新读取并恢复。

内核的任务状态机不认识 `ModelReply`、工具名或循环步骤。

## 3. 模型和工具接口

### 模型输入

`ModelInput` 包含任务编号、当前步骤、**原顺序上下文条目**和允许使用的工具声明。上下文不被合并、重排或暗中截断。

模型后端返回 `BackendResult::Ok(ModelReply)`：

```json
{
  "content": "准备查找",
  "tool_calls": [
    {"id": "call-1", "name": "lookup", "arguments": {"key": "x"}}
  ],
  "usage": {"prompt_cache_hit_tokens": 128}
}
```

没有工具调用即表示本轮给出最终结果。模型协议、流式 token 和提供方特定行为由后端适配器实现。

### 工具

每个 `ToolDefinition` 包含名称、描述、参数描述和内核服务路由。模型只能使用配置里存在的工具名，不能自己指定任意服务或可执行命令。

参数描述会传给模型，但首版**不实现通用 JSON Schema 校验器**；后端必须校验参数。内核仍独立检查实际服务操作权限，工具出现在声明里不等于调用者一定获授权。

一次模型回复里的多个工具调用按顺序执行，不做任意副作用并发。不同任务可以并行推进。

## 4. 上下文与配对

循环写入三种用户态消息：用户输入、模型输出、工具结果。工具调用的 ID 同步写入上下文配对字段：

- 模型输出打开调用 ID；
- 工具结果关闭对应 ID；
- 下一次模型请求能看到真正的工具结果，而不是仅有“执行过”的日志。

整批模型工具声明先校验：未知工具、重复 ID 或调用数超限会在执行前拒绝，避免前半批已产生副作用、后半批才发现非法。

遇初始上下文里未回答的工具调用，循环拒绝自动继续，要求明确恢复。首版不承诺进程崩溃后的工具恰好执行一次。

## 5. 停止、失败与取消

| 情况 | 处理 |
|---|---|
| 模型给出最终内容 | 写上下文，提交 `TaskFinish`，结束 |
| 达到模型步数上限 | 提交 `TaskFail`，不继续请求模型 |
| 模型错误或格式错误 | 任务失败，不编造输出 |
| 工具返回原生错误 | 原样作为工具结果写回，让下一步模型判断 |
| 内核拒绝工具、超时或后端退出 | 任务失败，不自动重试有副作用的操作 |
| 取消 | 提交任务取消，内核使关联请求失败，通知后端协作停止 |
| 取消与完成/失败竞争 | 以 `TaskGet` 或 `TaskEnded` 的真实内核终态为准 |
| 失败状态无法提交且任务仍运行 | `NeedsIntervention`，保留循环，不假报已结束、不再派工具 |

迟到或不相干的请求响应不会推进已经取消/终结的循环。已产生的外部副作用不可保证撤回。

循环是拉动状态机，没有内置墙钟线程。模型/工具调用超时由内核待办机制提供；自定义驱动也必须持续处理消息和超时。

## 6. 上下文快满时

循环在模型调用前读取压力信息。接近上限会：

1. 发出 `NeedsCompaction` 事件；
2. 暂停，不继续填窗口；
3. 外部策略生成摘要并调用 `ContextReplace`；
4. 收到替换通知后重新读取上下文，再继续。

纯状态机使用者也可调用 `resume_after_compaction()`。非暂停状态误调用会报错，但不会破坏当前进度。

如果工具已经执行、结果暂时写不进窗口，循环保留这份结果等待压缩，恢复后**只补写结果，不重复执行工具**。无法压缩时保持暂停，或由宿主取消；不偷偷删内容。

默认计量是序列化字节数的简单估计，**不是精确 token 数，也不是安全上界**。可替换 `LoopConfig.meter`。提供方系统提示、工具声明等额外成本需要模型适配器正确预算；首版不能保证所有提供方都不溢出。

## 7. 计量与事件

- `ModelOutput` 事件保留该步模型回执中的原生 usage。
- 最终结果只携带总计不超过 16 KiB 的 usage 样本，超限计入 `usage_dropped`，避免观测数据挤爆任务完成请求。
- 发布事件只做诊断，不进入模型上下文。超大诊断发布成简短标记，本地事件 API 仍保留完整内容。
- 诊断发布失败可通过 `take_report_error()` 取出；不因为缺少事件发布权限就把成功任务变失败。
- 本地事件和通知队列必须被驱动消费，不能无限积压。队列不足时保留未交付事件并明确报错。

## 8. 运行

项目目录里：

```sh
cargo test --workspace --all-targets
cargo build --workspace --bins
cargo run -p ithink-loop-demo
```

本工作区 Windows：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\dev.ps1 loop-demo
```

演示输入 `17 + 25`，经历两次模型请求、一次工具执行，最终得到 `42`。不用 API Key、不联网、不启动替代 Web 服务。

## 9. 已验证范围与限制

- 单个插件内，任务甲一直等模型时，任务乙仍可完成；取消甲后任务丙仍能正常运行。
- 真实内核权限不足时工具不会执行；模型错误不影响该插件的其他任务。
- 工具结果真实写回、配对保留；压缩恢复不会重复执行工具。
- 支持步数、单步工具数和条目数上限；行协议约 1 MiB，内联模型载荷更小，超大上下文应由用户态压缩/拆分。
- SDK 只有读取转移到后台线程，写管道仍同步，因此不承诺硬实时或完全异步 I/O。
- 核心循环本身不实现模型协议或 token 流式展示；可选的 OpenAI 兼容适配器与 Web 宿主已经提供 SSE 流式展示。尚无并行工具调度、自动重试、自动摘要或完整检查点恢复。它们可以在后端/驱动层扩展，不冒充已经实现。
