# 俺寻思🤔 内核设计草案

> 状态：0.1 原型对应草案，接口尚未稳定。原讨论中助手给出的未获确认的强制要求已撤回。具体实现范围见[首版实现约定](<实现约定.md>)，插件行为见[插件协议](<插件协议.md>)。

## 一、定位

- 独立、通用的开源 harness 项目，不是某个前端或业务产品的附属模块。
- 理念：**轻、快、模块化**。三者没有未经用户确认的强制排序；性能数字须实测，不以语言选型代替测试。
- 使用 Rust。插件采用独立进程，内核负责启动、运行时加载和替换。
- 参考操作系统的机制与策略分离，不机械复制 Linux 的所有概念或权限制度。
- 支持用户态实现主代理协调、工作代理执行的 super-agent 架构，但不在内核固定某种派活拓扑。

## 二、三个部件

```text
内核
├─ 通信调度器：事件消息的接收、编号、订阅与投递
├─ 任务管理器：任务归属、状态、上下文及受控替换
└─ 主体管理：AID、工作层级、显式权限与主体关系
```

插件生命周期、公开 API 和系统交互桥为三个部件提供入口。

### 2.1 通信调度器

负责把消息送到明确目的地，不负责决定“这件工作应该派给谁”。

- 消息保留内核绑定的来源身份。
- 使用调用者指定的主题串起消息，内核为主题编号和维护订阅。
- 已订阅者直接接收，无需把每条消息先交主代理理解。
- 不强行把所有通信变成父子关系；任务归属树不限制所有事件路由。
- 有界进程消息通道，过载显式处理，不无限积压。

这里不使用“事由”作为强制业务概念；同一主题代表什么由用户态定义。

### 2.2 任务管理器

任务和主体是两个东西：一个主体可以同时拥有多个任务；任务编号与 AID 独立。

任务的父子关系只表示归属和取消传播，不表示模型窗口继承。

```text
任务甲（AID 甲所有）
├─ 任务乙（可由 AID 乙所有，初始上下文明确传入）
└─ 任务丙（可由 AID 丙所有，初始上下文明确传入）
```

- 父主体可给子主体创建任务并提供初始内容。
- 上层主体管理生命周期，不自动读取下层后续私有上下文。
- 子任务结果返回上级；结束通知也交给所属主体。
- 取消向下传播，以迭代方式处理，避免深层递归使内核栈溢出。
- 任务结束使关联待办系统请求失败并通知后端；已发生的外部副作用不能保证撤回。
- 不把“新会话”规定为开新树或新子树。会话如何映射任务与上下文完全属于用户态。

### 2.3 主体管理

主体包含 AID、父主体、工作层级、能力集合和活动状态。

| 级别 | 工作含义 |
|---|---|
| 0 | 用户/宿主入口 |
| 1 | 主 agent 层级，预期长期存在 |
| 2 | 负责干活的 worker |
| 3 | 一次性子代理 |

这些数字描述工作层级，**不自动表示权限大小、CPU 优先级或运行时长**。

- 权限通过显式能力授予，不通过“官阶”推导。
- 消息不能自报任意 AID；调用身份绑定到实际插件连接。
- 直接创建主体时不能提升层级或扩大能力。
- 通过宿主预授权的插件模板可委托执行能力，主代理不需要自己持有所有工具权限。
- 主代理“基本不能死”是目标，但不能解释成不允许宿主关闭程序。第一版只隔离插件故障；持续监督、恢复与重启另行实现。

## 三、上下文与压缩

### 3.1 原文历史和当前视图分开

- 原文、追加和替换记录保存在上下文历史中。
- 当前视图是本次可交给模型适配器的内容。
- 压缩替换当前视图，不覆写原始历史。
- 日志和视图当前在内存里；能序列化单个上下文日志并回放，不等于已经实现整核持久恢复。

### 3.2 内核负责的机制

1. 每个任务分别核算容量、输出预留和压力阈值。
2. 接近阈值通知任务所属主体；超过硬上限拒绝写入，不偷偷丢旧内容。
3. 提供带预期版本号的范围替换，失败不部分提交。
4. 校验声明的工具调用配对边界，不切断未闭合配对。
5. 不修改固定项；替换必须实际缩小计量单位。
6. 大上下文支持分页读取，写入结果返回版本与用量，不强行返回整份内容。

初始版本的计量单位和配对标记由调用方提供，内核不假称理解全部模型消息结构或拥有精确 token 计量器。

**不能将多个父子任务的上下文使用量相加后，对照单个模型的窗口上限。** 总内存、调用成本、并发配额是另一类资源账，后续可以独立增加。

### 3.3 用户态负责的策略

- 何时主动请求压缩、选择哪段、保留多少近期信息。
- 用独立模型摘要、原代理摘要、引用外置还是其他方式。
- 提供方特定的计量和缓存优化。

不内置默认剪头尾、默认丢最旧。未装摘要插件时仍可运行，但到上限会明确报错；不承诺无限运行。

### 3.4 缓存

未替换的上下文保留原样，不为“整理”擅自改写或重排。是否为了节省窗口而接受一次缓存失效，由压缩插件决定。

不把 DeepSeek 的缓存单元机制固化为所有模型的内核规则。缓存命中为提供方的尽力行为，不能靠本地字段保证。真实命中统计应由模型适配器采集；首版尚未实现在线模型适配器。

## 四、插件装载与公开接口

- 内核启动插件进程，通过有大小限制的逐行 JSON 进行双向交互。
- 握手提供协议版本、AID 和实例代数；只有初始化确认后的实例才能被激活。
- 新实例失败保留旧实例；热替换成功后撤销旧身份、订阅、服务及待办请求。
- 加载和卸载处理依赖关系，拒绝缺失和成环依赖。
- 子代理启动使用宿主批准的模板，不接受模型任意传入可执行路径。
- 插件安装、下载、市场与应用专用拓扑在用户态。
- 热替换不自动迁移插件内存，未来状态迁移需要独立协议。

## 五、系统交互桥

```text
调用方插件 -> 内核（权限检查、路由、记录）-> 后端插件
调用方插件 <- 内核（原样封装结果）     <- 后端插件
```

- 内核不内置 bash/read/write 的业务工具实现。
- 真实系统、远程系统或测试后端都可以成为桥的另一端。
- 宿主可以按服务和操作分权；例如读和写需要不同能力。
- 后端结果与原始错误消息不归一化。内核自己拒绝、超时或连接失效是另一类错误。
- 慢操作异步回报，不阻塞内核等结果。取消通知是协作机制，不是撤回副作用的承诺。

## 六、安全与故障隔离

**独立进程不等于安全沙箱。** 原生程序如果恶意绕过协议，仍可能直接调用操作系统。只有额外的 OS 限制才能真正强制“所有系统访问必须过桥”。

首版实现 Windows Job / Unix 进程组清理和管道线程回收，用于插件退出、卸载和替换的生命周期管理。它不替代恶意代码隔离、文件范围沙箱或凭据保护。

## 七、验证与后续

首版的验收重点是：

- 主体权限不能由插件自报提升。
- 主代理能通过公开 API 启动子代理、传上下文、收结果。
- 后台慢操作或插件握手期间，其他请求仍可被处理。
- 热替换失败保留旧实例，成功后不会接受旧实例迟到消息。
- 压缩替换原子、原文可回放，不拆配对、不静默截断。
- 取消与卸载能结束待办请求，退出时清理受管进程树。

后续另行设计：整核持久化、常驻主体恢复、安全沙箱、流式大数据通道（token 增量已有临时事件，不等同于大载荷通道）、长期日志保留和性能基准。许可证尚未决定。
